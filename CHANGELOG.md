# Changelog

All notable changes to `@quox/ward` are documented here. This project adheres
to the WARD protocol version it implements (currently v0.2).

## [Unreleased]

### WARD v0.2 protocol support (breaking hash scheme, additive API)

Implements the WARD v0.2 spec revision: canonical-JSON chain hashing
(SPEC §4.4) under canonicalization profile **WARD-CANON-1** (SPEC §3.2),
replacing v0.1's pipe-delimited concatenation to close a delimiter-injection
gap (a crafted `ward_entry_id`/`source_id` containing `|` could make two
distinct field tuples hash identically). Existing v0.1 chains remain
verifiable; the writer will not create new v0.1 entries.

#### Added
- `chainHashV2` (exported): SHA-256 of the canonical JSON of an entry's 10
  required hash-body fields (SPEC §4.4). Throws if any of the 10 fields is
  absent or null (the hash body must contain exactly these members).
- `buildEntry`/`appendEntry` default `ward_version` to `"0.2"`; `buildEntry`
  throws if asked to create a `"0.1"` entry, or a `chain_id` containing `"::"`
  (SPEC §5.2, §16.1).
- `verifyChain` selects the hash scheme **per entry** from its own
  `ward_version` (VERIFICATION.md §3 Step 2): `"0.2"` canonical-JSON, `"0.1"`
  legacy concatenation (SPEC Appendix A, verify-only), any other value is
  `BROKEN`/`CHAIN_HASH_MISMATCH` with a detail naming the unrecognized
  version. A v0.1 entry whose `ward_entry_id`/`source_id` contains `"|"` now
  adds a warning (delimiter-injection exposure).
- New **Step 0** (VERIFICATION.md §3): validates every entry's
  well-formedness before any hash is recomputed — all 11 required fields
  present and correctly typed, 64-hex hash fields, `seq` in
  `[1, 2^53 - 1]`, no null hash-body members, well-formed-NFC hash-body
  strings, no `"::"` in `chain_id`. Failure is `BROKEN`/`SCHEMA_INVALID`
  (new reason code) with a detail naming the failing field and rule.
- **Version monotonicity** (SPEC §16.1): once any entry declares `"0.2"`, a
  later entry declaring `"0.1"` is `BROKEN`/`VERSION_DOWNGRADE` (new reason
  code).
- `canonicalize` now implements canonicalization profile WARD-CANON-1 in
  full: object keys sorted by **UTF-8 byte order** (`isWellFormedNfc` +
  `Buffer.compare`, not JS's default UTF-16 code-unit sort — these differ for
  supplementary-plane characters), strings must already be well-formed
  Unicode in NFC (rejected, never silently normalized), integers bounded to
  `+/-(2^53 - 1)`, non-finite numbers rejected. `isWellFormedNfc` is exported.
- `parseStrictJson` (new module `src/strict-json.ts`, exported): a
  dependency-free hand-written JSON parser that rejects duplicate object
  member names (SPEC §3.2 rule 5). Wired into `FileStore`'s NDJSON reads and
  the `ward-verify` CLI's chain-export/anchor-file reads — the two places
  untrusted WARD bytes enter the SDK. `verifyChain` itself takes
  already-parsed objects, which cannot represent a duplicate key, so this
  rule is enforced at the parse boundary, not inside the verifier.
- `conformance/fixtures/spec-v0.2/` and `conformance/spec-v0.2-vectors.test.ts`:
  vendors the WARD spec repo's own `examples/single-chain` and
  `examples/meta-chain` fixtures verbatim (every hash, payload_hash, and
  signature is real, generated by `ward/tools/gen-examples.mjs`) and
  recomputes all of them independently, anchoring the v0.2 scheme against a
  source outside this repo.

#### Changed
- `WARD_VERSION` is now `"0.2"`. `LEGACY_WARD_VERSION` (`"0.1"`) is exported
  for callers that need to name the retired scheme explicitly.
- The verifier's INTACT result `ward_version` field now reports the **head
  entry's own declared version**, not a hardcoded constant — a chain may
  contain v0.1 entries followed by v0.2 entries if the writer upgraded
  mid-chain.
- Vendored JSON schemas (`schemas/*.json`) updated to the spec repo's current
  v0.2 versions: `chain_id` pattern rejecting `"::"`, `seq` maximum
  `9007199254740991`, the WARD meta-chain `source_id` grammar, and the two
  new BROKEN reason codes.
- Existing v0.1 fixtures (`conformance/fixtures/*.json`,
  `test/writer-verifier.test.ts`) are unchanged as data, but now exercise the
  Appendix A legacy-scheme path explicitly rather than the writer's default.

#### Previous pass: adversarial-audit hardening

Closes key-binding, anchoring, downgrade, and torn-write findings; anchors the
hash math against independently-computed vectors.

### Added
- Key binding: `deriveKeyId(publicKey)` (exported) and verifier binding of a
  tip's `key_id` to the verifying key, with `verifyChain(..., { expectedKeyId })`
  for opaque/DID key_ids. New reason code `KEY_ID_MISMATCH`.
- External anchor: `verifyChain(..., { anchor: { expectedTip, expectedHeadSeq } })`
  to defeat tail-rewrite, plus `ward-verify --anchor <tip.json>`. New reason
  code `TRUNCATED_BEHIND_ANCHOR`; anchor breaches also surface `TIP_MISMATCH`
  with `details.anchor: true`.
- Signature enforcement: `verifyChain(..., { requireSignatures: true })` and
  `ward-verify --require-signed`. New reason code `SIGNATURE_REQUIRED`; a
  signed-capable tip that arrives unsigned now emits a warning.
- External conformance vectors (`conformance/external-vectors.test.ts`):
  SPEC §4 genesis + entry hashes recomputed with `node:crypto` only and pinned
  as hex literals, breaking the SDK-generated-fixture circularity.

### Fixed
- `FileStore` recovers from a torn final line (crash mid-append) via
  `getWarnings`, instead of making the whole chain unreadable. A parse failure
  on any non-final line still throws (real corruption).

### Changed
- README documents the out-of-band anchor workflow and a full reason-code table.
- SPEC-POINTERS documents the `key_id` derivation spec gap.

## [0.1.0] 2026-07-25

Initial standalone release. WARD v0.1 chain math + verification, packaged as a
zero-dependency library.

### Added
- Crypto primitives (`sha256`, `genesisHash`, `chainHash`, `canonicalize`,
  `payloadHash`), SPEC §3.2, §4.
- Chain math writer helpers (`buildEntry`, `appendEntry`, `headOf`,
  `chainDescriptor`, `computeTip`), SPEC §4, §11.
- Verifier (`verifyChain`) returning a spec-conformant
  `ward_verification_result` with all seven reason codes, VERIFICATION.md
  §3-§5.
- Ed25519 tip signing (`generateKeypair`, `signTipHash`, `verifyTipSignature`,
  PEM helpers) via `node:crypto`, SPEC §4.5, §12.2.
- Pluggable storage: `WardStore` interface, `InMemoryStore`, and file NDJSON
  `FileStore` (both enforce gap-free seq + source uniqueness).
- `ward-verify` CLI: verify a chain export file, exit `0/1/2/3`.
- Conformance fixture corpus (valid + signed-tip + one tamper per reason code)
  and a Vitest suite validating outputs against the four spec JSON schemas.

### Not included (out of core, by design)
- CMS / X.509 tip anchoring (needs `pkijs`/`asn1js`), use `ward-service`.
- SQLite-backed store, a future optional peer; implement `WardStore` to add it.
